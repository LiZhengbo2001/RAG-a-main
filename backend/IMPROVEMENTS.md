# RAG Agent 优化提升清单

## 一、检索质量

### 混合检索
当前只有向量检索。加 BM25 关键词检索做 RRF 融合，召回率能提 10-20%，性价比最高的单点优化。

### 重排序
检索取 top_k 后加交叉编码器精排（如 bge-reranker-v2-m3），把真正相关的文档排到前面。

### 查询改写
当前 thinking 事件里写了"查询改写"但 query 原样传给 embedding，没有做任何真正的改写。加 query expansion（同义词扩展、子问题拆分），对模糊和复杂问题效果明显。

### Milvus 索引
IVF_FLAT 精度最高但速度不是最优。HNSW 更快，IVF_SQ8 更省内存——根据场景选择合适的索引类型。

---

## 二、LLM 生成

### Prompt 模板化
当前 system prompt 是写死的字符串。抽成配置文件或数据库存储，支持 A/B 测试不同 prompt 变体。

### 上下文窗口控制
当前所有 chunk 全塞进去，没有 token 计数和截断逻辑。加 `tiktoken` 计算长度 + 动态截断，防止撑爆 LLM 上下文窗口。

### 结构化输出
当前纯文本输出。如果要做自动化下游处理，强制 LLM 输出 JSON 格式，Ollama 已原生支持 JSON mode。

### 模型升级
7b 模型推理快但能力有限。试 qwen2.5:14b 或 deepseek-r1:8b，对比同一批问题的引用准确率和幻觉率。

---

## 三、Agent 推理编排

### 当前是固定流程而非 Agent
用户问 → 检索 → 生成，全程硬编码。LLM 没有"自主决策"能力——不知道该不该检索、该换什么查询词、该不该重搜。

### ReAct / Tool Calling
Ollama 支持 function calling。把检索定义为工具，让 LLM 自己决定何时调、传什么参数、结果够不够。

### LangGraph 替代手写 pipeline
当前 `run_stream` 是 80 行的 async generator。用 LangGraph 声明式定义节点 + 条件边，支持循环（检索不满意 → 改写查询 → 再检索）。

### Self-Reflection
生成完后让 LLM 自检"引用编号是否准确？有没有编造的内容？"，不合格则重新生成，显著提升答案可靠性。

---

## 四、文档处理

### CSV / JSON 解析未实现
前端列了支持格式，后端 `parse_file` 只有 PDF、DOCX、MD、TXT 四种格式的实现。

### 表格处理
`pypdf` 取文字时 PDF 里的表格变成乱码。换 `Unstructured` 库可以正确解析表格结构。

### 图片忽略
多模态 RAG 当前完全未做。`ColPali` 或 `Unstructured` 能提取图片的视觉特征和描述文字。

### 分块策略单一
512 字符固定窗口。进阶方案：语义分块（按 embedding 相似度判断断点）或结构分块（Markdown 按标题层级、PDF 按章节）。

### 增量更新
当前只能整篇删除 + 整篇重新上传。加文档指纹（hash + mtime）做增量索引，只处理变化部分。

## 五、系统架构

### Embedding 性能瓶颈
nomic-embed-text 逐条调 Ollama API，10 个 chunk 的文档需要串行 10 个 HTTP 请求。改用 batch 调用或本地模型一次性编码。

### 数据库连接池
切 MySQL 后 `aiomysql` 支持连接池，当前每请求新建会话，可加 `pool_size` 参数提升并发能力。

### 文件存储
`UPLOAD_DIR` 在 backend 的本地目录下。部署多副本时不同实例文件不同步，需切对象存储（MinIO / S3）或统一 NFS。

### 日志系统
当前靠 `print` 和 uvicorn 默认日志。换 `structlog` 做结构化 JSON 日志，方便接入 ELK / Loki 检索。

### 监控
检索耗时、生成耗时、token 数、错误率、并发量全部不可见。加 `prometheus_client` + Grafana 做监控大盘。

---

## 六、安全性

### 密码强度校验缺失
注册时不限制密码长度和复杂度。

### 接口限流
任何人不限次数调 `/auth/login` 暴力破解。加 `slowapi` 或 Redis 做频率限制。

### 请求体大小限制
上传文档没有上限，恶意传超大文件可撑爆磁盘。

### CORS 配置
`allow_origins=["http://localhost:5173"]` 仅覆盖开发场景，部署后需改为实际域名。

---

## 七、前端体验

### 功能缺失
- 无暗色模式
- 无国际化（i18n），所有文案硬编码中文
- 对话标题为第一条消息前 20 字，可改为 LLM 自动生成
- 不能编辑、复制、重新生成单条消息
- KnowledgeBase 文档列表无搜索、过滤、分页
- 对话列表无搜索功能

### 交互细节
- 上传文档时无进度条或分块进度提示
- 错误提示直接透传后端异常信息（如"sqlite3.IntegrityError"而非"保存失败"）

## 八、评估与测试

### 自动化测试
`tests/` 目录下三个文件均为空。缺少单元测试（retriever、chunker）和集成测试（上传 → 检索 → 生成端到端链路）。

### RAG 质量评估
不知道系统实际表现如何。RAGAS 四个指标（faithfulness / answer relevancy / context precision / context recall）用 LLM 当裁判打分，零人工标注成本。

### 性能基准
不知道单次检索平均耗时、首 token 延迟、不同长度文档的处理时间，无法度量优化效果。

---

## 优先级建议

1. **混合检索** —— 性价比最高，检索质量立竿见影
2. **评估体系** —— 没有度量就无法优化，先建基线
3. **上下文窗口控制** —— 防止长文档撑爆 LLM 窗口，解决实际问题
4. **结构化日志 + 监控** —— 从"盲飞"到"可观测"
5. **Agent 推理编排** —— 从固定流程到自主决策，架构质的飞跃
6. **前端细节打磨** —— 提升日常使用体验
7. **多模态文档** —— 处理表格和图片，拓展适用范围
